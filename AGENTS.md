# Operación de cv_automatico_ai con FALEXOM y Spec Kit

- Autoridad: `.specify/memory/constitution.md`, SPEC activo y estas reglas operativas. No alterar la Constitución sin enmienda aprobada.
- Un SPEC usa una sola rama `NNN-nombre`, coincidente con `specs/NNN-nombre/` y `.specify/feature.json`. Una historia incremental usa una única rama `NNN-slug` o `feature|fix/US-NNN-slug`, vinculada de forma inequívoca a su archivo aprobado en `specs/stories/` (estado `APROBADA_PARA_DESARROLLO`); el integrador la reconoce en modo historia sin exigir `spec.md`, `plan.md`, `tasks.md` ni modificar `feature.json`. La historia aprobada es el contrato funcional y no se modifica durante su implementación. Nunca implementar funcionalidades en `main`. Detener escrituras ante discrepancias, HEAD separado o trabajo ajeno que pueda perderse.
- Orchestrator coordina con el mínimo equipo necesario. Developer comprueba Git y ejecuta los scripts; Analyst redacta Specify/Clarify y registra historias incrementales; Architect Plan; Project Manager Tasks; Developer Implement; QA valida independientemente; Security interviene según riesgo. Los especialistas no delegan.
- Preparación: Developer utiliza `python3 .specify/scripts/falexom-workflow.py prepare nombre-corto "objetivo autorizado"` sobre main limpio. Reanudar con `resume NNN-nombre`; nunca duplicar SPEC/ramas ni reconstruir contexto por suposición. Las historias incrementales se registran y ramifican por el flujo autorizado de Analyst (rama propia y commit documental inicial con aprobación humana); no usan `prepare` ni `resume`. Consultar `.specify/FALEXOM.md`.
- Usar los comandos, scripts y plantillas reales de Spec Kit. Orchestrator transmite a cada especialista las instrucciones pertinentes y sus rutas autorizadas. Developer genera estructura/checklists y ejecuta scripts; la redacción especializada sigue en su responsable. No invocar `opencode run --command` directamente. Para CLI usar el adaptador local documentado.
- Antes de delegar desarrollo, Orchestrator verifica que existan AGENTS.md, Constitución y ejecutor. Encarga a Developer únicamente `resume NNN-nombre` y `check` como preparación, sin cambios de producto. Solo autoriza desarrollo tras recibir BASE_READY, rama, HEAD, MAIN y SPEC coherentes. Si faltan archivos o la base está desactualizada, detenerse y solicitar preparación humana; no desarrollar primero.
- Antes de cada fase y escritura, Developer ejecuta `python3 .specify/scripts/falexom-workflow.py check`. Los scripts comprueban rama/SPEC o rama/historia según el contexto detectado (señales SPEC explícitas; en su ausencia, la historia aprobada y commiteada como contrato); los permisos estáticos de edit no son una protección condicional por rama. No escribir producto si el control falla.
- Mantener aprobación humana de spec y plan del workflow instalado; registrar la decisión en la conversación/artefacto pertinente. Clarify consulta únicamente decisiones imprescindibles no resueltas. Checklists incompletos requieren la decisión prevista por Implement. No inventar aprobaciones.
- Pruebas proporcionales al riesgo conforme a la Constitución, aunque una plantilla las considere opcionales. Reutilizar evidencia vigente; diferenciar prueba ejecutada, pendiente y bloqueada. QA no sustituye aceptación humana.
- Staging/commit local: exclusivamente Developer, encargo autorizado, rama/SPEC o rama/historia coherentes, rutas explícitas revisadas y permiso shell efectivo; usar `stage` y `commit` del ejecutor local. El commit no equivale a cierre ni aprobación funcional. Merge a main requiere aprobación humana expresa y ejecución manual; push nunca automático. No reset destructivo, clean, force push ni cambios innecesarios en ramas históricas.
- No cambiar credenciales, perfiles, agentes, integración/harness ni controles para sortear un bloqueo. Shell permanece en ask; nunca --auto ni grants persistentes amplios. El ejecutor no es una sandbox del SO.
- Estado heredado: SPEC-002 cerrado; SPEC-001 T063/T064 pendientes; SPEC-003 no iniciado. No reabrir/cerrar/iniciar esos trabajos sin un encargo nuevo. El alcance de cada sesión lo determina su encargo autorizado; no deducir autorización funcional de la instalación operativa.

- Fast-forward de main hacia la rama SPEC y merge de la rama SPEC hacia main son operaciones distintas. Un fast-forward posible no implica permiso del harness: si la actualización es necesaria y no está autorizada, pedir intervención humana inmediatamente. No sustituir un merge denegado por otra herramienta ni habilitar permisos generales.
