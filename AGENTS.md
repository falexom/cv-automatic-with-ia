# Operación de cv_automatico_ai con FALEXOM v2 y Spec Kit

- Autoridad operativa: `AGENTS.md` es la referencia principal de gobernanza del proyecto. La Constitución conserva autoridad sobre principios y restricciones; el SPEC o la historia aprobados definen el contrato funcional. `.specify/FALEXOM.md` es complementario y debe ser coherente con estas reglas. No alterar la Constitución sin enmienda aprobada.
- Flujo principal: Codex/OpenCode Plan → SpecKit (Constitution, Specify, Clarify, según corresponda) → historias aprobadas → planificación de tareas → Build → verificaciones técnicas → aceptación funcional y visual humana → QA/seguridad según riesgo → cierre Git. Se conservan la estructura, comandos y plantillas nativos de SpecKit para especificación; las incompatibilidades de la integración instalada se detallan en `.specify/FALEXOM.md` y bloquean el paso afectado, sin autorizar su elusión.
- Plan/Build es el flujo principal. Plan analiza requisitos y el proyecto en modo de solo lectura, y propone historias pequeñas con criterios de aceptación; no modifica archivos. Cada funcionalidad o fix independiente requiere su propia historia expresamente aprobada, incluso si deriva de un SPEC. Constitution, Specify y Clarify escriben sus artefactos solo en una fase de escritura autorizada; no se ejecutan como escrituras dentro de Plan. Antes de implementar es obligatoria una descomposición técnica de tareas y verificaciones, registrada en la conversación o en un artefacto autorizado y proporcional al riesgo. En el flujo incremental no se exigen `plan.md`, `tasks.md` ni el comando Implement de SpecKit; `tasks.md` es opcional y los requisitos del ciclo SPEC clásico permanecen si se utiliza. Tras la aprobación expresa del usuario a una historia concreta, Build comprueba que árbol e índice estén limpios y autorizados, crea una rama de trabajo desde la base aprobada y registra únicamente el contrato aprobado en `specs/stories/`. El commit documental inicial contiene solo ese Markdown, tras revisar exactamente el diff staged. Después Build ejecuta `check` y solo implementa si devuelve `MODE=story` y `BASE_READY=true`. Un SPEC usa una sola rama `NNN-nombre`, coincidente con `specs/NNN-nombre/` y `.specify/feature.json`. Una historia incremental usa una única rama `NNN-slug` o `feature|fix/US-NNN-slug`, vinculada de forma inequívoca a su archivo aprobado en `specs/stories/` (estado `APROBADA_PARA_DESARROLLO`); el integrador la reconoce en modo historia sin exigir `spec.md`, `plan.md`, `tasks.md` ni modificar `feature.json`, pero conserva los controles de rama, base y aprobación. Si coinciden señales de SPEC e historia, el integrador bloquea para resolución manual. El modo incremental no sustituye ni elude controles SpecKit aplicables. La historia aprobada es el contrato funcional y no se modifica durante su implementación. Nunca implementar funcionalidades en `main`; no iniciar rama de trabajo con cambios no autorizados. Detener escrituras ante discrepancias, HEAD separado o trabajo ajeno que pueda perderse.
- No se requieren perfiles especializados, Orchestrator ni adaptadores de agentes como requisito metodológico del flujo Plan/Build. Esto no elimina las dependencias todavía codificadas o documentadas en la integración instalada; detener el paso incompatible conforme a `.specify/FALEXOM.md`. Los especialistas siguen disponibles de forma opcional: Orchestrator coordina; Analyst apoya Specify/Clarify; Developer apoya implementación; Architect diseño; Project Manager tareas; QA revisión independiente; Security revisión según riesgo. Cuando se usen, sus responsabilidades y aprobaciones respetan este documento; ningún especialista delega.
- En el flujo incremental, Plan entrega la propuesta sin escribirla; Build crea la rama y el commit documental solo después de la aprobación expresa de esa historia y con permisos efectivos. No iniciar rama si árbol o índice tienen cambios no autorizados. Tras ese commit, `check` debe confirmar la historia aprobada. Para flujos SPEC, Build usa `python3 .specify/scripts/falexom-workflow.py prepare nombre-corto "objetivo autorizado"` sobre main limpio y `resume NNN-nombre` para reanudar una rama SPEC existente; no usar esos comandos para historias ni duplicar ramas o reconstruir contexto por suposición. Consultar `.specify/FALEXOM.md`.
- Cuando un flujo SPEC requiera Spec Kit, conservar sus comandos, scripts y plantillas reales. Build puede ejecutar directamente los pasos autorizados que la integración y los permisos efectivos permitan; el apoyo especializado es opcional metodológicamente, pero las dependencias aún vigentes de comandos y adaptador bloquean el uso nativo del paso afectado hasta su migración autorizada. No invocar `opencode run --command` directamente. Para CLI usar el adaptador local documentado.
- Antes de implementar, Build confirma que existen `AGENTS.md`, la Constitución y el ejecutor. En una historia incremental ejecuta `check`; en una rama SPEC existente, primero `resume NNN-nombre` y luego `check`. `resume` acepta únicamente ramas SPEC. Solo continúa con `MODE=story` y `BASE_READY=true` en el flujo incremental, o con el contexto SPEC coherente y listo en el flujo SPEC. Si faltan archivos, el modo no coincide o la base está desactualizada, detenerse y solicitar resolución humana.
- Antes de cada fase de implementación y de cada escritura de producto posterior al commit documental inicial, Build ejecuta `python3 .specify/scripts/falexom-workflow.py check`. En modo historia, el archivo aprobado debe estar committeado en HEAD y se aplican los mismos controles de rama y base que SPEC; no se altera `feature.json`, aunque el código aún lo lee y exige un JSON legible con `feature_directory` incluso en modo historia. Los permisos estáticos de edit no son una protección condicional por rama. No escribir producto si el control falla.
- Plan no escribe archivos. El usuario aprueba expresamente la historia antes de que Build cree la rama o escriba el contrato; esa aprobación concreta autoriza el commit documental inicial, sujeto a permisos efectivos. Después de las verificaciones y la aceptación funcional y visual del usuario, Build requiere autorización correspondiente antes de staging y commit de implementación/cierre. En flujos SPEC se mantienen las aprobaciones humanas de especificación y plan que ya exige el workflow. Registrar decisiones en la conversación/artefacto pertinente. Clarify solo resuelve decisiones imprescindibles. Si se utiliza Implement en el ciclo SPEC clásico, sus checklists incompletos requieren la decisión humana prevista por ese comando; no es un requisito adicional del flujo incremental. No inventar aprobaciones.
- Priorizar verificaciones técnicas de código (sintaxis, tipos, lint, compilación según corresponda) y pruebas focalizadas en el cambio. No ejecutar suites completas ni pruebas funcionales automatizadas sin autorización humana, salvo controles técnicos mínimos indispensables por riesgo o exigencias vigentes de la Constitución/contrato; justificar y comunicar esa excepción. El Principio XXI exige cobertura automatizada suficiente en capacidades críticas. Reutilizar evidencia vigente y distinguir verificaciones ejecutadas, pendientes y bloqueadas. La aceptación funcional y visual corresponde exclusivamente al usuario. Después de ella, realizar revisión QA y de seguridad según riesgo, sin agentes personalizados obligatorios; si aparecen cambios funcionales, repetir la aceptación afectada antes del cierre.
- Staging/commit local: Build puede crear la rama y registrar como commit documental inicial únicamente el Markdown de la historia aprobada, tras la aprobación expresa de esa historia y si los permisos efectivos lo permiten. Antes, verifica índice y árbol limpios/autorizados; revisa que el diff staged contenga exactamente ese archivo y nunca lo hagas en `main` ni incluyas código u otros archivos. Si un permiso efectivo bloquea la operación, detenerse sin buscar otra herramienta ni ampliar permisos. Tras aceptación funcional y visual y autorización correspondiente, Build realiza commits de implementación mediante `stage` y `commit` del ejecutor local, con rutas explícitas revisadas y diff staged verificado exactamente antes de cada commit. El commit documental no equivale a implementación, aceptación funcional ni integración. Merge a main requiere aprobación humana expresa y ejecución manual; push nunca automático. No ejecutar merge, push, rebase, reset, clean, force push ni otras operaciones destructivas sin la autorización correspondiente.
- No cambiar credenciales, perfiles, agentes, integración/harness ni controles para sortear un bloqueo. Shell permanece en ask; nunca --auto ni grants persistentes amplios. El ejecutor no es una sandbox del SO.
- La fuente de estado y prioridades es `docs/roadmap.md`; no mantener estados históricos de SPEC en la gobernanza. El alcance de cada sesión lo determina su encargo autorizado; no deducir autorización funcional de la instalación operativa ni del roadmap.

- Fast-forward de main hacia la rama SPEC y merge de la rama SPEC hacia main son operaciones distintas. Un fast-forward posible no implica permiso del harness: si la actualización es necesaria y no está autorizada, pedir intervención humana inmediatamente. No sustituir un merge denegado por otra herramienta ni habilitar permisos generales.
