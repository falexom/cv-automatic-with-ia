# Operación de cv_automatico_ai con FALEXOM y Spec Kit

- Autoridad operativa: `AGENTS.md` es la referencia principal de gobernanza del proyecto. La Constitución conserva autoridad sobre principios y restricciones; el SPEC o la historia aprobados definen el contrato funcional. `.specify/FALEXOM.md` es complementario y debe ser coherente con estas reglas. No alterar la Constitución sin enmienda aprobada.
- Plan/Build es el flujo principal. Plan analiza requisitos y el proyecto en modo de solo lectura, y propone historias pequeñas con criterios de aceptación; no modifica archivos. Tras la aprobación expresa del usuario a una historia concreta, Build comprueba que árbol e índice estén limpios y autorizados, crea una rama de trabajo desde la base aprobada y registra únicamente el contrato aprobado en `specs/stories/`. El commit documental inicial contiene solo ese Markdown, tras revisar exactamente el diff staged. Después Build ejecuta `check` y solo implementa si devuelve `MODE=story` y `BASE_READY=true`. Un SPEC usa una sola rama `NNN-nombre`, coincidente con `specs/NNN-nombre/` y `.specify/feature.json`. Una historia incremental usa una única rama `NNN-slug` o `feature|fix/US-NNN-slug`, vinculada de forma inequívoca a su archivo aprobado en `specs/stories/` (estado `APROBADA_PARA_DESARROLLO`); el integrador la reconoce en modo historia sin exigir `spec.md`, `plan.md`, `tasks.md` ni modificar `feature.json`, pero conserva los controles de rama, base y aprobación. Si coinciden señales de SPEC e historia, el integrador bloquea para resolución manual. El modo incremental no sustituye ni elude controles SpecKit aplicables. La historia aprobada es el contrato funcional y no se modifica durante su implementación. Nunca implementar funcionalidades en `main`; no iniciar rama de trabajo con cambios no autorizados. Detener escrituras ante discrepancias, HEAD separado o trabajo ajeno que pueda perderse.
- No se requiere Orchestrator ni un especialista FALEXOM para el flujo Plan/Build. Los especialistas siguen disponibles de forma opcional: Orchestrator coordina; Analyst apoya Specify/Clarify; Developer apoya implementación; Architect diseño; Project Manager tareas; QA revisión independiente; Security revisión según riesgo. Cuando se usen, sus responsabilidades y aprobaciones respetan este documento; ningún especialista delega.
- En el flujo incremental, Plan entrega la propuesta sin escribirla; Build crea la rama y el commit documental solo después de la aprobación expresa de esa historia y con permisos efectivos. No iniciar rama si árbol o índice tienen cambios no autorizados. Tras ese commit, `check` debe confirmar la historia aprobada. Para flujos SPEC, Build usa `python3 .specify/scripts/falexom-workflow.py prepare nombre-corto "objetivo autorizado"` sobre main limpio y `resume NNN-nombre` para reanudar una rama SPEC existente; no usar esos comandos para historias ni duplicar ramas o reconstruir contexto por suposición. Consultar `.specify/FALEXOM.md`.
- Cuando un flujo SPEC requiera Spec Kit, conservar sus comandos, scripts y plantillas reales. Build puede ejecutar directamente los pasos autorizados; si se usa Orchestrator o un especialista, este transmite las instrucciones y rutas autorizadas sin convertirlo en requisito. No invocar `opencode run --command` directamente. Para CLI usar el adaptador local documentado.
- Antes de implementar, Build confirma que existen `AGENTS.md`, la Constitución y el ejecutor. En una historia incremental ejecuta `check`; en una rama SPEC existente, primero `resume NNN-nombre` y luego `check`. `resume` acepta únicamente ramas SPEC. Solo continúa con `MODE=story` y `BASE_READY=true` en el flujo incremental, o con el contexto SPEC coherente y listo en el flujo SPEC. Si faltan archivos, el modo no coincide o la base está desactualizada, detenerse y solicitar resolución humana.
- Antes de cada fase de implementación y de cada escritura de producto posterior al commit documental inicial, Build ejecuta `python3 .specify/scripts/falexom-workflow.py check`. En modo historia, el archivo aprobado debe estar committeado en HEAD y se aplican los mismos controles de rama y base que SPEC; no se usa ni altera `feature.json`. Los permisos estáticos de edit no son una protección condicional por rama. No escribir producto si el control falla.
- Plan no escribe archivos. El usuario aprueba expresamente la historia antes de que Build cree la rama o escriba el contrato; esa aprobación concreta autoriza el commit documental inicial, sujeto a permisos efectivos. Después de las verificaciones y la aceptación funcional y visual del usuario, Build requiere autorización correspondiente antes de staging y commit de implementación/cierre. En flujos SPEC se mantienen las aprobaciones humanas de especificación y plan que ya exige el workflow. Registrar decisiones en la conversación/artefacto pertinente. Clarify solo resuelve decisiones imprescindibles; checklists incompletos requieren la decisión prevista por Implement. No inventar aprobaciones.
- Pruebas proporcionales al riesgo conforme a la Constitución, aunque una plantilla las considere opcionales. Reutilizar evidencia vigente; diferenciar prueba ejecutada, pendiente y bloqueada. QA no sustituye aceptación humana.
- Staging/commit local: Build puede crear la rama y registrar como commit documental inicial únicamente el Markdown de la historia aprobada, tras la aprobación expresa de esa historia y si los permisos efectivos lo permiten. Antes, verifica índice y árbol limpios/autorizados; revisa que el diff staged contenga exactamente ese archivo y nunca lo hagas en `main` ni incluyas código u otros archivos. Si un permiso efectivo bloquea la operación, detenerse sin buscar otra herramienta ni ampliar permisos. Tras aceptación funcional y visual y autorización correspondiente, Build realiza commits de implementación mediante `stage` y `commit` del ejecutor local, con rutas explícitas revisadas y diff staged verificado exactamente antes de cada commit. El commit documental no equivale a implementación, aceptación funcional ni integración. Merge a main requiere aprobación humana expresa y ejecución manual; push nunca automático. No ejecutar merge, push, rebase, reset, clean, force push ni otras operaciones destructivas sin la autorización correspondiente.
- No cambiar credenciales, perfiles, agentes, integración/harness ni controles para sortear un bloqueo. Shell permanece en ask; nunca --auto ni grants persistentes amplios. El ejecutor no es una sandbox del SO.
- Estado heredado: SPEC-002 cerrado; SPEC-001 T063/T064 pendientes; SPEC-003 no iniciado. No reabrir/cerrar/iniciar esos trabajos sin un encargo nuevo. El alcance de cada sesión lo determina su encargo autorizado; no deducir autorización funcional de la instalación operativa.

- Fast-forward de main hacia la rama SPEC y merge de la rama SPEC hacia main son operaciones distintas. Un fast-forward posible no implica permiso del harness: si la actualización es necesaria y no está autorizada, pedir intervención humana inmediatamente. No sustituir un merge denegado por otra herramienta ni habilitar permisos generales.
