# Operación de cv_automatico_ai con FALEXOM y Spec Kit

- Autoridad: `.specify/memory/constitution.md`, SPEC activo y estas reglas operativas. No alterar la Constitución sin enmienda aprobada.
- Un SPEC usa una sola rama `NNN-nombre`, coincidente con `specs/NNN-nombre/` y `.specify/feature.json`. Una historia incremental usa una única rama `NNN-slug` o `feature|fix/US-NNN-slug`, vinculada de forma inequívoca a su archivo aprobado en `specs/stories/` (estado `APROBADA_PARA_DESARROLLO`); el integrador la reconoce en modo historia sin exigir `spec.md`, `plan.md`, `tasks.md` ni modificar `feature.json`, pero conserva los controles de rama, base y aprobación. Si coinciden señales de SPEC e historia, el integrador bloquea para resolución manual. La historia aprobada es el contrato funcional y no se modifica durante su implementación. Nunca implementar funcionalidades en `main`. Detener escrituras ante discrepancias, HEAD separado o trabajo ajeno que pueda perderse.
- Orchestrator coordina con el mínimo equipo necesario. Analyst redacta Specify/Clarify y registra historias incrementales; para una historia aprobada puede preparar su rama y realizar únicamente el staging y commit documental inicial conforme al punto 12. Developer prepara y ejecuta el flujo Spec Kit, implementa código y realiza commits de implementación; Architect redacta Plan; Project Manager, Tasks; QA valida independientemente; Security interviene según riesgo. Los especialistas no delegan.
- Preparación: Developer utiliza `python3 .specify/scripts/falexom-workflow.py prepare nombre-corto "objetivo autorizado"` sobre main limpio. Reanudar con `resume NNN-nombre`; nunca duplicar SPEC/ramas ni reconstruir contexto por suposición. Las historias incrementales se registran y ramifican por el flujo autorizado de Analyst (rama propia y commit documental inicial con aprobación humana); no usan `prepare` ni `resume`. Consultar `.specify/FALEXOM.md`.
- Usar los comandos, scripts y plantillas reales de Spec Kit. Orchestrator transmite a cada especialista las instrucciones pertinentes y sus rutas autorizadas. Developer genera estructura/checklists y ejecuta scripts; la redacción especializada sigue en su responsable. No invocar `opencode run --command` directamente. Para CLI usar el adaptador local documentado.
- Antes de delegar desarrollo, Orchestrator verifica que existan AGENTS.md, Constitución y ejecutor. Para un SPEC existente, encarga a Developer `resume NNN-nombre` y `check`; para una historia incremental ya preparada por Analyst, encarga solo `check` (`resume` acepta únicamente ramas SPEC). Solo autoriza desarrollo tras recibir BASE_READY, rama, HEAD, MAIN y el contexto SPEC o historia aprobado y coherente. Si faltan archivos o la base está desactualizada, detenerse y solicitar preparación humana; no desarrollar primero.
- Antes de cada fase de implementación y de cada escritura de producto posterior al commit documental inicial, Developer ejecuta `python3 .specify/scripts/falexom-workflow.py check`. El modo historia requiere que el archivo aprobado ya esté committeado en HEAD y pasa los mismos controles de rama y base que SPEC; no usa ni altera `feature.json`. Los permisos estáticos de edit no son una protección condicional por rama. No escribir producto si el control falla.
- Mantener aprobación humana de spec y plan del workflow instalado; registrar la decisión en la conversación/artefacto pertinente. Clarify consulta únicamente decisiones imprescindibles no resueltas. Checklists incompletos requieren la decisión prevista por Implement. No inventar aprobaciones.
- Pruebas proporcionales al riesgo conforme a la Constitución, aunque una plantilla las considere opcionales. Reutilizar evidencia vigente; diferenciar prueba ejecutada, pendiente y bloqueada. QA no sustituye aceptación humana.
- Staging/commit local: en una historia incremental aprobada, Analyst puede preparar su rama y registrar únicamente el archivo Markdown aprobado como commit documental inicial, con autorización humana específica y si los permisos efectivos lo permiten. Debe revisar que el índice esté vacío y que el diff staged contenga exactamente ese archivo; nunca hacerlo en `main` ni incluir código u otros archivos. Si el permiso efectivo bloquea la operación, detenerse sin buscar otra herramienta ni ampliar permisos. Developer conserva los commits de implementación y usa `stage` y `commit` del ejecutor local para rutas explícitas revisadas, con autorización y permiso shell efectivo. El commit documental no equivale a implementación, aceptación funcional ni integración. Merge a main requiere aprobación humana expresa y ejecución manual; push nunca automático. No reset destructivo, clean, force push ni cambios innecesarios en ramas históricas.
- No cambiar credenciales, perfiles, agentes, integración/harness ni controles para sortear un bloqueo. Shell permanece en ask; nunca --auto ni grants persistentes amplios. El ejecutor no es una sandbox del SO.
- Estado heredado: SPEC-002 cerrado; SPEC-001 T063/T064 pendientes; SPEC-003 no iniciado. No reabrir/cerrar/iniciar esos trabajos sin un encargo nuevo. El alcance de cada sesión lo determina su encargo autorizado; no deducir autorización funcional de la instalación operativa.

- Fast-forward de main hacia la rama SPEC y merge de la rama SPEC hacia main son operaciones distintas. Un fast-forward posible no implica permiso del harness: si la actualización es necesaria y no está autorizada, pedir intervención humana inmediatamente. No sustituir un merge denegado por otra herramienta ni habilitar permisos generales.
